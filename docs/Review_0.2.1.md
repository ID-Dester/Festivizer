## Исходный дефект и стратегия

09.11.2026 был запущен `artifacts/publish/win-x64-zorder-test/GarlandForWindows.exe`, PID 22508, версия 0.2.0. SHA-256 exe `3085F0B9C0428B0909E4A3C2633721853E1980358B046EA99BA17F9F8285DB42`, DLL `5BF846ACC1D6C659C80E7B1DBF776FD941D63ACBD0FBD80225555A4977ABD3BF`. При активации Проводника визуально наблюдалась частично закрытая окном рамка. Переход через настройки отдельно не воспроизведён; точное время старта и снимок не сохранены. Процесс, запущенный для проверки, завершён принудительно, а не через трей. Причину именно этого эпизода по одному снимку установить нельзя.

Для текущей реализации `FrameOverlayController` создаёт отдельный WPF overlay с owner текущего допустимого HWND и уничтожает прежний экземпляр при смене цели. Проверяются foreground, PID, разрешённые стили, owner и фактический порядок; при неверном порядке выполняется одна коррекция, затем рамка скрывается. При стабильном положении координаты обновляются без подъёма по Z-order. Событие foreground собственного процесса больше не отбрасывается; предусмотрены сброс при меню/настройках и объединённое обновление после DPI. Для отказа создания/позиционирования той же цели введена задержка повтора 5 секунд. Taskbar остаётся отдельной.

Это предварительная реализация: пользовательское окно с недоступной owner-связью может остаться без рамки; наблюдался отказ доступа, на котором прототип до ограничения повторов многократно пересоздавал окно. Поддержку приложений с другим уровнем прав не заявляем.

### Замечания

#### A01 — P2: штатные события меню отбрасываются до обработки

**Место:** [ApplicationHost.cs](../src/GarlandForWindows/ApplicationHost.cs), `OnWinEvent`, строка 120 на момент проверки; регистрация hook — строка 68.

Фильтр `objectId != 0 || childId != 0` выполняется до обработки `EVENT_SYSTEM_MENUSTART/MENUEND`. Для обычного меню Windows передаёт `OBJID_MENU` или `OBJID_SYSMENU`, поэтому эти сообщения не доходят до изменения `systemMenuOpen`. Кроме того, диапазон hook не включает уже объявленные `MENUPOPUPSTART/END`. Это пробел обработки разных типов меню; ручные обработчики `ContextMenuStrip` покрывают только собственный трей. Контракты параметров описаны в [Event Constants Microsoft](https://learn.microsoft.com/en-us/windows/win32/winauto/event-constants).

**Исправление:** обрабатывать системные menu-события до фильтра оконных object-событий, учитывать допустимые object IDs и нужные popup-события; добавить проверки маршрутизации. Визуальная доступность системного меню в одном smoke-тесте не доказывает, что этот обработчик работает.

#### A02 — P2: флаг открытого меню может навсегда отключить рамку

**Место:** [ApplicationHost.cs](../src/GarlandForWindows/ApplicationHost.cs), присваивание `systemMenuOpen` в строке 123 и условие показа в строке 163.

Флаг глобальный: после принятого MENUSTART он сбрасывается только принятым MENUEND. При пропущенном/отфильтрованном завершении ни смена foreground, ни сверка раз в 500 мс не проверяют действительное состояние меню. `Refresh` продолжает выполнять `frame.Clear("menu open")` для следующих допустимых окон. Microsoft отдельно отмечает, что MENU-события не всегда образуют точные пары. Это вывод по коду и контракту событий, а не воспроизведённое зависание в GUI этого аудита.

**Исправление:** привязать состояние меню к контексту/окну и восстанавливать его по реальному состоянию Windows, предусмотреть потерянный END и переход к другому окну. Добавить сценарии непарных и вложенных событий, а также восстановления рамки после них; не использовать бессрочный глобальный boolean как единственное основание скрытия.

#### A03 — обязательные сценарии контроллера остаются непроверенными

В модельном тестовом проекте `FrameOverlayController` не компилируется; оконный тест также обходит его. Пока не проверены обязательные по §7.1 ТЗ переходы A → B, A → настройки → B, устаревший DPI callback после смены поколения, пересоздание после уничтожения owner/native HWND и сбои освобождения именно через контроллер.

**Нужно:** тестируемый адаптер операций окна/foreground для контроллера и сценарии его конечного состояния; затем ручные переходы через настройки на текущем идентифицированном кандидате. Проходящие `FrameOrder` и `FrameRetryGate` проверяют только части алгоритма. Это пробел приёмки, а не установленный сбой каждого перечисленного сценария.

Отсутствие ухода рамки за окно в коротком тесте Проводника — положительный результат, но не закрытие исходных переходов через настройки/DPI.
