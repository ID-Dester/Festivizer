# Проверка версии 0.1

**Дата:** 09.11.2026.  
**Объект:** исходники, находившиеся в рабочей папке на момент проверки; это не проверка опубликованного Git-тега.  
**Среда:** Windows 11 x64, сборка ОС 22631; .NET SDK 10.0.403, MSBuild 18.9.15.  
**Итог:** рабочий прототип, успешные сборки и частично подтверждённое GUI-поведение. Полная приёмка по §14 исходного ТЗ пока не подтверждена.

## 1. Фактически выполненные проверки

Команды выполнялись из корня проекта через установленный `dotnet.exe`:

```powershell
dotnet build GarlandForWindows.sln -c Release --nologo
dotnet run --project tests/GarlandForWindows.Tests -c Release --no-build
dotnet build GarlandForWindows.sln -c Debug --no-restore --nologo
dotnet publish src/GarlandForWindows/GarlandForWindows.csproj -c Release -r win-x64 --self-contained true -o artifacts/publish/win-x64 --nologo
```

Для CLI использовались `DOTNET_CLI_HOME` в корне проекта и `DOTNET_CLI_TELEMETRY_OPTOUT=1`; для публикации — существующий кэш `.nuget/packages` через `NUGET_PACKAGES`.

При публикации возникло предупреждение **NU1900**: сервис NuGet для получения сведений об уязвимостях был недоступен (`https://api.nuget.org/v3/index.json`). Публикация завершилась, но проверку уязвимостей нельзя считать успешно выполненной.

GUI проверялся через Windows computer-use на существующем окне Проводника. Tray-only приложение не предоставило инструменту отдельного targetable-окна; ошибка инструмента о его отсутствии сама по себе не означала неудачный запуск. Процесс и видимые декорации проверены отдельно. Запущенный для проверки процесс затем завершён как уборка тестового окружения; **штатный выход через меню трея этим не проверен**.

## 2. Замечания по коду

P1 — исправить до приёмки следующей версии; P2 — исправить в рамках стабилизации 0.2. Ниже отдельно обозначены выводы по коду: это не результаты воспроизведения всех отказов на GUI.

### R01 — P1: сбой настройки overlay не приводит к безопасному скрытию

**Места:** [GarlandOverlay.cs](../src/GarlandForWindows/GarlandOverlay.cs), `SourceInitialized` и `Place`; [Native.cs](../src/GarlandForWindows/Native.cs), объявления interop; [ApplicationHost.cs](../src/GarlandForWindows/ApplicationHost.cs), `Refresh`.

Возвраты `SetWindowLongPtr` и `SetWindowPos` не проверяются. Если установка `WS_EX_TRANSPARENT`/`WS_EX_NOACTIVATE` не удалась, окно всё равно показывается. Если позиционирование не удалось, overlay может остаться на старом месте. Для этих вызовов не включено сохранение Win32 last-error, поэтому нет достоверной диагностики причины. `SetWindowLongPtr` требует различать нулевое предыдущее значение и ошибку.

Кроме того, исключение вокруг Taskbar обрабатывается отдельно, а аналогичной изоляции вокруг `frame.Place` и анимации нет. Исключение оконного overlay в Dispatcher может завершить всё приложение, нарушая независимость декораций. Это вывод по обработке отказов; сами отказы в этой проверке не инъецировались.

**Нужно:** проверяемые interop-обёртки, подтверждение безопасных стилей до первого показа, скрытие или закрытие только неисправного overlay, ограниченные по частоте логи и проверка частично неудачного запуска/завершения.

### R02 — P2: `HWND_TOP` не привязывает рамку к Z-order целевого окна

**Места:** [ApplicationHost.cs](../src/GarlandForWindows/ApplicationHost.cs), `Refresh`, вызов `frame.Place(bounds, Native.HWND_TOP)`; [GarlandOverlay.cs](../src/GarlandForWindows/GarlandOverlay.cs), `Place`.

Комментарий обещает положение непосредственно над активным окном, но `HWND_TOP` поднимает overlay наверх его группы и не указывает целевой HWND. В обычной группе он также не гарантирует положение поверх активного topmost-окна, которое текущий фильтр допускает. Эти случаи не покрыты проверкой одного Проводника.

**Нужно:** описать и проверить стратегию для обычных окон и перекрывающих popup; topmost-цели либо поддержать отдельной проверенной стратегией, либо явно исключить. Не считать существующий комментарий доказательством корректного Z-order.

### R03 — P2: высота полосы Taskbar конфликтует с единицами WPF

**Места:** [ApplicationHost.cs](../src/GarlandForWindows/ApplicationHost.cs), `RefreshTaskbar`, прямоугольник высотой 30 пикселей; [GarlandOverlay.cs](../src/GarlandForWindows/GarlandOverlay.cs), `OnRender`, условие `h < 20`.

`SetWindowPos` получает физические размеры, а `ActualHeight` и рисунок WPF используют DIP. При масштабе 175% высота 30 физических пикселей составляет примерно 17,14 DIP, при 200% — 15 DIP. Оба значения меньше 20: рендер возвращается без рисунка. Также физический отступ рамки 12 пикселей расходится с отступами рисунка в DIP.

Это расчёт по коду, не результат смены системного масштаба в данной проверке.

**Нужно:** единая политика физических координат и DIP, размеры декорации в DIP с преобразованием для Win32; проверить 100%, 150%, 175%, 200% на одном мониторе.

### R04 — P2: статичная геометрия и ресурсы создаются на каждом кадре

**Места:** [GarlandOverlay.cs](../src/GarlandForWindows/GarlandOverlay.cs), `OnRender` и `DrawSide`.

Каждый кадр создаёт `Pen`, `StreamGeometry`, кисти свечения и ламп, повторно вычисляет точки. `Freeze()` нового пути не делает его кэшированным между кадрами. Это расходится с требованием не пересоздавать статичную геометрию без необходимости. Фактическая загрузка CPU/GPU и GC пока не измерена.

**Нужно:** кэш геометрии по размеру/DPI/теме, повторное использование подходящих ресурсов и отдельное обновление яркости; снять замеры до и после изменения.

### R05 — P2: фильтр класса окна используется и для fullscreen

**Места:** [ApplicationHost.cs](../src/GarlandForWindows/ApplicationHost.cs), `IsCandidate` и `Refresh`.

`Windows.UI.Core.CoreWindow` безусловно исключён по классу, после чего геометрия и fullscreen вообще не проверяются. Если обычное пользовательское полноэкранное приложение использует этот класс, Taskbar-overlay останется разрешённым. Аналогично один общий фильтр смешивает исключение оболочки с допустимостью украшения приложения. Конкретный такой fullscreen-клиент в этой проверке не запускался.

**Нужно:** отдельные решения «это поверхность оболочки/собственная поверхность», «это fullscreen-конфликт», «это допустимая цель рамки»; не распознавать всю оболочку по одному общему классу.

### R06 — P2: первичная очередь Dispatcher не объединяет поток событий

**Место:** [ApplicationHost.cs](../src/GarlandForWindows/ApplicationHost.cs), `QueueRefresh`.

`pending` устанавливается только внутри первого `BeginInvoke`. До его выполнения каждый WinEvent уже успевает добавить отдельный делегат в Dispatcher. Число полных `Refresh` частично сокращается, но начальная очередь остаётся пропорциональна числу событий. Задержки под нагрузкой не измерялись.

**Нужно:** объединять запросы до постановки в очередь с учётом вызова из `SystemEvents`, не копить устаревшие операции и проверять завершение до обновления overlay.

## 3. Что реализовано корректно на уровне структуры

- Основа — WPF, а `NotifyIcon` и меню взяты из Windows Forms; собственного WinForms `Form` в проекте нет.
- `App.xaml` использует `ShutdownMode="OnExplicitShutdown"`; mutex имеет область пользовательского сеанса.
- Включён Per-Monitor V2 через manifest; наличие manifest не доказывает правильное преобразование всех размеров.
- `SetWinEventHook` вызывается с флагом `0`, который соответствует `WINEVENT_OUTOFCONTEXT`: это не отсутствие нужного режима. Делегат удерживается полем `callback`.
- В обычном пути hooks создаются и снимаются в UI-потоке; полное поведение при отказах ещё требуется проверить.
- Есть обработка `TaskbarCreated`, базовая логика автоскрытия и полноэкранная геометрическая политика. Наличие кода не заменяет ручную проверку этих сценариев.

## 4. Непроверенные обязательные сценарии

- Полный click-through на лампах/свечении, resize-границах и элементах Taskbar; фокус клавиатуры.
- Браузер, многократные Alt+Tab, перекрывающие popup/topmost-окна, закрытие или сворачивание во время drag.
- Автоскрытие, включая запуск со скрытой Taskbar и включение/выключение этого режима.
- Fullscreen/borderless fullscreen реальных приложений, выход из них и восстановление декораций.
- Изменение DPI/разрешения, перезапуск Explorer и восстановление команд трея в обоих состояниях включения.
- Выключение/включение и штатный выход через трей, частичные отказы WinAPI, 100 переключений, 30 минут работы и замеры ресурсов.

Исправления и проверки включены в [ТЗ версии 0.2](../doc/GarlandForWindows_0.2_SPEC.md). Условия исходной приёмки остаются в [ТЗ 0.1](../doc/GarlandForWindows_SPEC.md).
