## Изменения

`WinEventRouter` различает foreground, системные menu/popup-события, move/resize и object-события; оконные фильтры не отбрасывают menu object ID. `MenuStateTracker` читает foreground/PID/thread до и после `GetGUIThreadInfo`: несогласованное состояние или ошибка даёт Unknown и скрывает оконную рамку. Существующая сверка раз в 500 мс переоценивает состояние при потерянном END. Состояние системного меню не хранится как глобальный постоянный флаг; собственное меню трея учитывается отдельно в том же решении видимости.

Если приложение использует нестандартное меню, которое не отражается флагами `GetGUIThreadInfo`, одни события инициируют повторную проверку, но не гарантируют обнаружения такого меню. Универсальная поддержка кастомных меню не подтверждена. Ошибки доступа к GUI-потоку логируются ограниченно, состояние Unknown скрывает только оконную рамку.

Контроллер использует подставляемые адаптеры фактов, overlay и очереди, а также часы. При ошибке освобождения старая рамка сначала скрывается; пока живой HWND не удалось освободить, новая рамка не создаётся. Старые DPI-callback после смены поколения/Dispose игнорируются. Реальные автозапуск и реестр пользователя не изменялись.

### Замечание к воспроизводимости DesktopTests

Оконный тест выдал **9 PASS**, затем **FAIL**, код выхода **1**:

```text
FAIL desktop integration: System.Exception: controller test foreground is target
Program.cs:line 43
```

Это не SKIP. Низкоуровневые owner/Z-order, hide/show и закрытие первой цели прошли. Проверки menu-mode, Win32 popup и настоящего контроллера в этом запуске **не выполнялись**, поскольку исключение возникло раньше.

В [тесте](../tests/GarlandForWindows.DesktopTests/Program.cs) после `target.Show(); target.Activate();` используется фиксированный `Task.Delay(300)`, а затем однократно проверяется foreground. Результат `Activate()` не учитывается. Наличие доступного интерактивного desktop само по себе не обеспечивает получение foreground тестовым окном. Прежнее добавление паузы не устранило нестабильность этого предусловия.

**Нужно до повторного подтверждения оконных проверок:** заменить фиксированную паузу ограниченным ожиданием фактического foreground с обработкой сообщений, записывать результат активации и наблюдаемый HWND, отличать срыв предусловия теста от провала алгоритма рамки. Если среда не позволила получить foreground, последующие сценарии не помечать PASS; не повышать устойчивость теста принудительным обходом ограничений Windows на фокус. Провести новый оконный прогон в контролируемом сеансе и сохранить его полный результат.

Этот отказ не доказывает ошибку производственного приложения и не опровергает исторический успешный запуск из предыдущего раздела. Он означает, что полный положительный результат оконного теста при перепроверке не воспроизведён.

### Полнота закрытия A01–A03

Изменения A01–A02 подтверждены кодом: menu-события маршрутизируются до оконного object-фильтра, глобального `systemMenuOpen` больше нет, состояние читается заново у текущего GUI-thread. Для A03 появились настоящие тесты контроллера с адаптерами, включая смену A/B, устаревшие callback, ошибки и восстановление.

Для утверждения о полном выполнении ТЗ нужна таблица соответствия обязательных сценариев §4.1–4.2 конкретным тестам и результатам. Например, проверки отдельных routing-входов и смены флагов сами по себе не подтверждают всю последовательность повторных/непарных событий через host; обобщённый `Eligible=false` не является отдельной проверкой Win32-адаптера для каждого minimize/maximize/cloak/topmost-состояния. Такие границы следует обозначать явно, даже если общий алгоритм допуска проверен.

**Итог проверки отчёта:** описание архитектурных изменений и хеши согласуются с проектом; статус «не принято» обоснован. Автотесты логики воспроизведены, полный оконный прогон — нет. До приёмки остаются устойчивый оконный тест, явная карта покрытия обязательных сценариев и ручная матрица на идентифицированной публикации.
