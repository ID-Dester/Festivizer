# Garland for Windows — доработка меню и жизненного цикла рамки

**Планируемая версия:** 0.2.2.  
**Версия документа:** 1.0, 10.11.2026.  
**Статус:** задание на реализацию; изменения ещё не выполнены.  
**Основание:** замечания A01–A03 повторной проверки [0.2.1](../docs/Review_0.2.1.md).  
**Платформа и стек:** Windows 11 x64, один монитор, C# / .NET 10 / WPF / Win32.

## 1. Цель и границы

Исправить потерю событий меню и исключить постоянное скрытие рамки после пропущенного события закрытия. Подтвердить тестами жизненный цикл **самого `FrameOverlayController`**, включая переходы через настройки, смену цели, DPI и уничтожение HWND.

Сохранить owner-привязку и контроль Z-order из 0.2.1, click-through, отсутствие активации, независимость Taskbar, работу трея, настроек и автозапуска. Новых пользовательских функций не добавлять.

Исходный результат проверки: 70 автопроверок и 9 проверок реальных тестовых HWND прошли; на одном Проводнике кандидат показывал рамку поверх окна. Это не полная приёмка 0.2.1: контроллер в тестах обходится, переходы через настройки/DPI не подтверждены всей матрицей. Зависание меню в коротком GUI-прогоне не воспроизведено; риск выявлен по коду и контрактам Win32.

## 2. Что исправить

| Задача | Текущая проблема | Требуемый результат |
|---|---|---|
| A01. Маршрутизация | `objectId != 0` отсекает штатные menu-события; hook не включает popup-события | Правильная обработка меню до фильтров оконных object-событий |
| A02. Состояние меню | Глобальный `systemMenuOpen` зависит от пары START/END и не сверяется с Windows | Состояние связано с текущим GUI-контекстом и восстанавливается при потерянном END |
| A03. Контроллер | Тесты проверяют вспомогательные политики и overlay напрямую | Проверены конечные состояния реального контроллера и его отложенные операции |

### 2.1. Маршрутизация событий

- Разделить обработку `EVENT_SYSTEM_FOREGROUND`, событий меню, move/resize и `EVENT_OBJECT_*`. Системные события проверять до фильтра, предназначенного для оконных объектов.
- Зарегистрировать и обработать `EVENT_SYSTEM_MENUSTART`, `MENUEND`, `MENUPOPUPSTART`, `MENUPOPUPEND`. Использовать именованные константы.
- Для START/END учитывать предусмотренные Win32 `OBJID_MENU`, `OBJID_SYSMENU`, `OBJID_WINDOW` и `CHILDID_SELF`. Не заменять это снятием фильтра со всех object-событий; сохранять проверку параметров по типу события.
- События своего foreground должны по-прежнему скрывать рамку на настройках. Собственные события геометрии/отрисовки не должны создавать рекурсивную очередь обновлений.
- Callback только запрашивает объединённую переоценку; UI и состояние контроллера меняются в Dispatcher. Не допускать выхода исключений через P/Invoke.
- Собственный `ContextMenuStrip.Opening/Closed` оставить отдельным источником сведений о трее, без двойного независимого управления видимостью рамки.

### 2.2. Состояние меню: Windows — источник истины

Убрать бессрочный глобальный флаг как единственное основание скрытия. События — повод перепроверить состояние, а не гарантированно парные команды «включить/выключить».

Базовая реализация — небольшой компонент `MenuStateTracker` либо эквивалентная выделенная ответственность:

- Получать GUI-thread текущего foreground и сведения через `GetGUIThreadInfo`; корректно задавать `GUITHREADINFO.cbSize`, сохранять документированный last-error.
- Использовать `GUI_INMENUMODE`, `GUI_POPUPMENUMODE`, `GUI_SYSTEMMENUMODE` и контекст `hwndMenuOwner`. Не требовать равенства menu-owner и foreground HWND: меню может принадлежать связанному окну того же GUI-контекста.
- Привязывать снимок состояния к foreground HWND/PID/thread и поколению контекста. Событие старого окна или результат старого отложенного запроса не изменяет состояние новой цели.
- При смене foreground получать новый снимок. Нельзя просто сбросить флаг и показать рамку, если у нового foreground действительно открыто меню.
- При закрытии меню без END очередная существующая резервная сверка должна обнаружить отсутствие menu-mode и вернуть рамку допустимой цели. Нового быстрого постоянного polling не добавлять.
- Вложенные меню и повторные START не считать простой строго сбалансированной парой. Закрытие подменю не разрешает рамку, пока меню текущего контекста остаётся открытым.
- START/END чужого неактивного окна не должен скрывать либо возвращать рамку текущей цели.
- Состояния собственного трея, собственных настроек и меню foreground учитывать совместно: закрытие одного источника не отменяет другой активный источник скрытия.

Для неподдерживаемого/custom-меню, сведения о котором не отражаются в `GetGUIThreadInfo`, проверить события и определить ограниченную по контексту стратегию. Не заявлять универсальную поддержку всех кастомных меню; подтверждённые ограничения записать в отчёт. Непарное custom-событие также не должно навсегда блокировать рамки остальных окон.

Если запрос Win32 не удался или foreground изменился во время запроса, возвращать **Unknown**, а не достоверное «открыто/закрыто». На время недостоверного состояния рамку безопасно скрыть, повторить проверку существующим механизмом, записать ограниченную диагностику. Unknown не наследуется новой целью. Постоянная ошибка API — отдельный диагностируемый отказ, а не «меню всё ещё открыто».

### 2.3. Видимость и восстановление

После согласованной проверки контекста рамка видима, только если одновременно выполнены условия:

```text
GarlandsEnabled && WindowFrameEnabled && EligibleCurrentForeground
&& !FullscreenConflict && MenuState == Closed
&& !OwnTrayMenuOpen && FrameHealthy
```

Здесь собственное окно настроек уже исключено из `EligibleCurrentForeground`. `FrameHealthy` определяется результатами создания, безопасных стилей, owner, позиционирования и Z-order; это не жёстко заданное `true`.

- После закрытия меню при достоверном состоянии Closed рамка должна вернуться через ближайшее объединённое обновление. При потерянном END — не позднее ближайшей резервной сверки 500 мс плюс один цикл Dispatcher на незагруженном рабочем столе.
- Перед возвращением заново читать foreground и проверять цель, не показывать рамку прошлого окна.
- Во время реально открытого меню рамка скрыта; не использовать таймаут, который без проверки Windows показывает её поверх всё ещё открытого меню.
- Открытие/закрытие меню не перезаписывает настройки пользователя. Выключенная гирлянда не включается после END или восстановления состояния.
- Сохранить не более одного актуального overlay, одну коррекцию Z-order на цикл и задержку после отказов. Не исправлять зависание глобальным Topmost, активацией цели или частыми подъёмами окна.

## 3. Тестируемость контроллера

Выделить узкие адаптеры чтения фактов Win32, операций/создания overlay и постановки отложенных действий. Время повторных попыток должно управляться тестовыми часами. Допускается сохранить WPF-обёртку в Windows-тестовом проекте; не требуется большой рефакторинг, новый DI-контейнер или смена стека.

Тесты должны вызывать настоящий `FrameOverlayController.Update`, `Clear`, `Configure`, `Dispose` и его реальные callback-пути. Отдельная модель, заново повторяющая алгоритм контроллера, не заменяет его проверку.

Fake-окружение должно независимо моделировать:

- foreground, PID, DPI, валидность и состояния target HWND;
- создание/уничтожение overlay, его owner, стили, видимость и относительный Z-order;
- очередь Dispatcher, которую тест может выполнить после смены поколения;
- отказы создания, позиционирования и освобождения;
- успех API при неверном конечном порядке окон.

Проверять конечные инварианты: рамка относится к актуальной цели, выше неё, безопасна для ввода, старый экземпляр освобождён, callback прошлого поколения ничего не меняет. Счётчики вызовов использовать только как дополнительное доказательство ограниченности ресурсов/повторов.

## 4. Обязательные автоматические сценарии

### 4.1. Маршрутизация и меню

| Сценарий | Проверка |
|---|---|
| START/END с `OBJID_MENU`, `OBJID_SYSMENU`, `OBJID_WINDOW` | Допустимые сочетания доходят до переоценки, не отбрасываются общим фильтром |
| Popup START/END | События зарегистрированы и обработаны |
| Меню ещё открыто, но пришёл END подменю | Рамка остаётся скрытой по актуальным сведениям Windows |
| Повторные START, END без START | Нет отрицательных счётчиков, зависания или неверного возвращения рамки |
| START → меню закрыто без END → резервная сверка | Рамка допустимой цели возвращается |
| START окна A → foreground B → запоздалый END A | Старый контекст не меняет состояние B |
| У B тоже открыто меню | Переход A → B не показывает рамку поверх меню B |
| Меню фонового окна, собственный трей и настройки | Источники корректно разделены; закрытие одного не отменяет другие |
| Ошибка `GetGUIThreadInfo` → успешный повтор | Unknown диагностируется, затем состояние восстанавливается |
| Выключение гирлянд при открытом меню | Закрытие меню не включает их обратно |

Тесты не должны открывать системные меню или менять реестр пользователя для моделирования этих последовательностей.

### 4.2. Жизненный цикл `FrameOverlayController`

1. Первый показ A, повторное обновление A и изменение настроек без лишнего пересоздания живого overlay.
2. Смена A → B: экземпляр A освобождён, owner/PID/границы соответствуют B, активна одна рамка.
3. A → собственные настройки → B: на настройках рамки нет, после перехода показывается B.
4. DPI-callback A поставлен в очередь → переключение B → выполнение callback A: B не скрывается, A не появляется заново.
5. Callback поставлен в очередь → `Dispose` → выполнение callback: ни нового HWND, ни обновления UI после завершения.
6. Уничтожение target или native HWND рамки: старый экземпляр не используется, следующая допустимая цель получает новый overlay.
7. Minimize/maximize/cloak/topmost/fullscreen/невалидный PID: рамка скрыта; возврат к допустимому состоянию восстанавливает её.
8. Ошибки создания, привязки, стилей, позиционирования и закрытия: безопасное скрытие, ограниченный повтор, освобождение остальных ресурсов.
9. Ошибка A и задержка повтора: сверка до истечения задержки не создаёт окна; тестовые часы разрешают восстановление, новая цель B не блокируется отказом A.
10. Успешный API при неверном Z-order: одна коррекция; при повторной неудаче рамка скрыта и ошибка диагностирована.

## 5. Оконная и ручная проверка

- Сохранить 70 прежних автопроверок и 9 проверок реальных HWND либо документировать их эквивалентную перегруппировку; количество PASS само по себе не является критерием.
- Расширить оконный тест прогоном через настоящий контроллер на тестовых окнах. Проверить выбор цели и восстановление рамки; прежний прямой вызов `GarlandOverlay` оставить как проверку низкого уровня.
- Подключить `GarlandForWindows.DesktopTests` к solution, чтобы Debug/Release компилировали его. Запуск GUI-тестов остаётся отдельным явным шагом, наличие проекта в сборке не означает их выполнение.
- При отсутствии интерактивного Desktop печатать SKIP и фиксировать его в отчёте отдельно от PASS.

На одной идентифицированной публикации проверить:

| Сценарий | Критерий |
|---|---|
| Проводник и названный браузер: системное/контекстное меню и подменю | Рамка скрывается, меню доступно, после закрытия рамка возвращается поверх текущей цели |
| Закрытие меню Escape, щелчком вне меню и выбором безопасного пункта | Одинаково корректное восстановление, без перехвата фокуса |
| A → настройки → A/B, Apply/Cancel/крестик | Не менее 20 циклов суммарно без исчезновения или ухода рамки за окно |
| Меню A → переход B и обратно | Нет зависания запрета для B и устаревших рамок |
| Трей, общий и отдельный выключатели | Нет самопроизвольного включения; значок, команды и Taskbar работают |
| 100 переключений, move/resize, закрытие цели | Один overlay, корректное освобождение и восстановление |
| DPI/разрешение и возврат в restored | Порядок и геометрия сохраняются; сценарии выполнить в согласованном тестовом сеансе |
| Штатный выход | Нет процесса, окон и действующих отложенных обновлений |

Сохранять путь, PID, версию и хеш DLL проверяемой сборки. Перед тестированием новой публикации штатно завершить прежний экземпляр: mutex может оставить запущенным старый бинарник. Не переносить GUI-результаты между разными хешами.

Артефакты:

- Исходники исправления и тесты.
- Публикация `artifacts/publish/win-x64-0.2.2-candidate` со всей средой выполнения.
- `docs/Review_0.2.2.md`: достигнутые состояния, команды и результаты, идентификация бинарников, GUI-наблюдения и непроверенные случаи.
- Актуальные README, Architecture и KnownLimitations. Закрывать A01–A03 только по фактическим результатам.

Доработка принимается, когда устранены A01–A02, завершены A03 и обязательные проверки этого документа. До этого статусы «код написан», «сборка», «поведение проверено» и «принято» фиксировать раздельно. NU1900 не скрывать и не считать успешным аудитом уязвимостей.

Ранее зарегистрированная проблема borderless fullscreen остаётся отдельным блокером общей приёмки 0.2. Принятие этой доработки не закрывает её автоматически. В рамках задания не менять fullscreen-эвристику, не добавлять новые темы/настройки, несколько мониторов, глобальный Topmost, инъекции, сеть и права администратора.

## 7. Технические источники и стартовый промпт

- [Event Constants](https://learn.microsoft.com/en-us/windows/win32/winauto/event-constants) — параметры menu-событий и ограничения их парности.
- [GetGUIThreadInfo](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getguithreadinfo) — чтение состояния foreground/GUI-thread, ошибки и переходы активации.
- [GUITHREADINFO](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-guithreadinfo) — menu-mode flags и `hwndMenuOwner`.

Изучи doc/GarlandForWindows_0.2.2_MenuAndLifecycle_SPEC.md,

В конце представь результаты проверок, идентификатор публикации,
непроверенные сценарии и блокеры общей приёмки.
