# Garland for Windows — стабилизация проверки и приёмка 0.2.2

**Версия документа:** 1.0, 10.11.2026.  
**Статус:** задание на доработку; изменения и повторная приёмка ещё не выполнены.  
**Основание:** [контрольная проверка отчёта 0.2.2](../docs/Review_0.2.2.md#контрольная-проверка-отчёта--10112026).  
**Объём:** тестовый стенд, покрытие требований и подтверждение результатов текущей версии.

## 1. Цель и исходное состояние

Сделать оконный тест воспроизводимым, явно сопоставить обязательные требования с проверками и повторить приёмку на идентифицированной публикации.

При контрольном прогоне Release собрался, набор логики выдал 127 строк PASS, хеши публикации совпали с отчётом. DesktopTests выдал 9 PASS и завершился с кодом 1 на `controller test foreground is target`, до popup и настоящего контроллера. В тесте результат `Window.Activate()` не проверяется, а получение foreground заменено паузой 300 мс.

Это срыв предусловия оконного сценария, который не доказывает дефект рамки. Исторический успешный прогон не отменяется, но его результат пока не воспроизведён. Не исправлять такой отказ изменением логики размещения рамки без отдельного подтверждённого дефекта.

Требования [основного ТЗ 0.2.2](GarlandForWindows_0.2.2_MenuAndLifecycle_SPEC.md) сохраняются. При изменении только тестов номер приложения остаётся 0.2.2; тестовую сборку и каждый прогон различать по идентификатору и хешам. Новых функций приложения не добавлять.

## 2. Стабилизация DesktopTests

### 2.1. Явные предусловия

- Перед созданием окон проверить доступность интерактивного default desktop. При его отсутствии завершить прогон со статусом SKIP до GUI-действий.
- Для сценариев меню и контроллера явно подготовить собственное тестовое target-окно. Обычный `Window.Activate()` допускается только для такого окна тестового стенда; производственные overlay не активировать.
- Записать результат активации, ожидаемый HWND/PID/thread и фактический foreground. Не считать вызов `Activate()` успешным только потому, что он не выбросил исключение.
- Проверять предусловия непосредственно перед зависимым сценарием. Наличие desktop не означает, что target получил foreground, а foreground первой цели не подтверждает активацию следующей.

### 2.2. Ожидание состояния

- Заменить `Task.Delay(300)` как единственную проверку готовности асинхронным ожиданием фактического условия `GetForegroundWindow() == target HWND`.
- Использовать монотонный отсчёт времени, предел **5 секунд** и недорогой интервал проверки **25–50 мс** либо эквивалентное событийное ожидание с дедлайном. Dispatcher должен продолжать обрабатывать сообщения.
- Не применять блокирующий `Thread.Sleep`, бесконечные циклы, произвольное увеличение фиксированной паузы или бесконечные попытки активации.
- Если нужное состояние не получено до дедлайна, закончить зависимый сценарий как BLOCKED. Последующие проверки, требующие этого foreground, отметить NOT_RUN; девять ранее успешных проверок не превращают весь прогон в PASS.
- При потере foreground во время сценария зафиксировать фазу и наблюдаемое окно. Потерю из-за вмешательства внешнего окна отделять от дефекта non-activation: если foreground получил сам overlay, это **FAIL**, а не BLOCKED.
- Не обходить ограничения Windows через `AttachThreadInput`, глобальный Topmost, принудительное переключение чужих окон, системные настройки или имитацию пользовательского ввода из тестового кода.

Для unattended-запуска, которому Windows не даёт активировать цель, предусмотреть контролируемый интерактивный запуск: пользователь запускает стенд/выбирает его тестовое окно, затем начинается прогон. Это отдельный способ установить предусловие, а не разрешение тесту перехватывать фокус у работающего пользователя.

### 2.3. Реальное меню и освобождение ресурсов

- Для Win32 popup ожидать подтверждённое Open с ограничением времени; после закрытия — подтверждённое Closed. Не подменять эти условия одним снимком по таймеру 250 мс.
- Предусмотреть дедлайн завершения popup и обязательную уборку: остановка таймеров, завершение своего меню, освобождение HMENU, закрытие overlay/целей и завершение тестового процесса.
- Уборка выполняется при PASS, FAIL, BLOCKED и исключениях. Не закрывать пользовательские окна и не завершать пользовательский экземпляр приложения как часть автоматической уборки теста.
- Ошибки закрытия ресурсов записывать; они не должны скрывать исходную причину отказа или препятствовать попыткам освободить остальные ресурсы.
- Сохранить низкоуровневые проверки owner/Z-order/hide/show и проверку настоящего контроллера. Не удалять упавшее утверждение и не заменять его безусловным успехом.

## 3. Формат результатов и диагностика

Принять явные статусы сценариев:

| Статус | Значение |
|---|---|
| PASS | Предусловия установлены, все утверждения сценария выполнены |
| FAIL | Проверка поведения либо уборки завершилась ошибкой |
| BLOCKED | Desktop есть, но необходимое предусловие не удалось установить или сохранить |
| SKIP | До GUI-действий подтверждено отсутствие подходящего интерактивного desktop |
| NOT_RUN | Сценарий не запускался из-за зависимости, остановки или выбранного набора |

Итоговый код процесса: **0 — весь обязательный набор PASS; 1 — FAIL; 2 — SKIP; 3 — BLOCKED**. Если присутствует FAIL, он имеет приоритет над BLOCKED. NOT_RUN из-за сорванного предусловия означает BLOCKED всего обязательного набора. Обновить команды/обёртки запуска под эти коды: SKIP и BLOCKED не считаются успешной приёмкой.

Для каждого прогона создавать уникальную папку `artifacts/validation/0.2.2/<run-id>/` с полным stdout/stderr и машиночитаемой сводкой. Записывать:

- run-id, время начала/окончания с часовым поясом и длительность;
- ОС, SDK/runtime, конфигурацию Debug/Release, команду запуска;
- путь, PID, версию и SHA-256 тестовой DLL; идентификатор исходников или набор хешей использованных исходных файлов;
- для GUI-приёмки — отдельные путь, PID, версию и SHA-256 exe/DLL приложения;
- результаты сценариев, количество PASS/FAIL/BLOCKED/SKIP/NOT_RUN и итоговый exit code;
- для отказа foreground — фазу, результат `Activate`, ожидаемый/фактический HWND и PID, длительность ожидания;
- сведения об уборке, включая оставшиеся собственные окна/ресурсы.

Не логировать заголовки или содержимое чужих окон. Не перезаписывать неудачный прогон последующим успешным. Повторы заранее ограничивать и сохранять все результаты.

## 4. Карта покрытия требований

Создать `docs/TestCoverage_0.2.2.md`. Включить **каждую строку §4.1 и каждый пункт §4.2** основного ТЗ, а также строки его ручной матрицы §5. Присвоить требованиям и сценариям устойчивые идентификаторы.

Минимальные колонки:

| Требование | Сценарий и условия | Проверяемый production-компонент | Уровень | Тест/ручной протокол | Результат и run-id | Пробел/ограничение |
|---|---|---|---|---|---|---|

Уровни различать: чистая политика/модель, настоящий контроллер с адаптерами, реальный Win32/WPF-адаптер, полное приложение в ручном GUI. Проверка одной функции не подтверждает автоматически остальные уровни.

Особенно проверить и закрыть либо явно отметить пробелы:

1. Повторные START, END без START, потерянный END и закрытие подменю — последовательности через настоящий путь маршрутизации/переоценки, а не только отдельные вызовы `IsMenuEvent`.
2. Старое событие A после перехода к B, в том числе когда у B открыто своё меню; события фонового окна.
3. Совместное действие меню, собственного трея и настроек; выключенные гирлянды не возвращаются после закрытия меню.
4. Unknown и восстановление после ошибки API/смены контекста; подтверждение резервной сверки при отсутствии END.
5. `FrameOverlayController`: A → B, A → настройки → B, устаревший DPI-callback, callback после Dispose, уничтожение HWND, ошибки и повторные попытки.
6. Minimize/maximize/cloak/topmost: общий тест `Eligible=false` проверяет реакцию контроллера, но не корректность фактов Win32-адаптера. Для каждого состояния указать, как проверен соответствующий адаптер/трекер; недоступное для реального GUI состояние проверить через узкий адаптер и явно обозначить уровень.
7. Корректный и неправильный конечный Z-order, включая одну коррекцию и безопасное скрытие при неудаче. Успешный возврат API не подменяет проверку порядка.

Дополнять тесты на реальных компонентах. Не копировать производственный алгоритм в тест для проверки его копии. Если несколько требований покрывает один сценарий, в карте описать, какие наблюдения подтверждают каждое из них; неподтверждённые части оставить открытыми.

## 5. Проверки самого стенда

Автоматически проверить механизм ожидания и классификацию без реальной задержки в 5 секунд: подставные монотонные часы/факты должны позволять детерминированный прогон.

- Foreground получен сразу и после нескольких обновлений — PASS предусловия без ожидания всего дедлайна.
- `Activate()` вернул false, но окно затем стало foreground — окончательное решение по факту и дедлайну, оба события отражены в диагностике.
- Foreground не получен — BLOCKED, зависимые сценарии NOT_RUN, итоговый код не 0.
- Desktop отсутствует — SKIP до создания окон и отдельный код результата.
- Overlay получает foreground после установленного предусловия — FAIL non-activation.
- Внешнее вмешательство или потеря desktop — отдельная причина BLOCKED с обязательной уборкой.
- Popup не открылся или не закрылся в пределах дедлайна — нет зависания теста и потерянных ресурсов; причина явно указана.
- Ошибка утверждения/закрытия — FAIL сохраняется в журнале и не заменяется успешным итогом.

## 6. Повторные прогоны и ручная приёмка

1. Собрать все проекты solution в Debug и Release; выполнить набор логики. Базовый результат — 127 строк PASS, но число строк не является критерием покрытия: перегруппировку тестов объяснить картой требований.
2. В согласованном спокойном сеансе заранее запланировать **по 5 полных запусков DesktopTests в Debug и Release**. Каждый запуск сохранять отдельно. Нельзя перезапускать до первого PASS и скрывать промежуточные результаты.
3. В контролируемой серии все обязательные оконные сценарии должны проходить. BLOCKED/SKIP объясняют непригодность среды, но не закрывают приёмку; после устранения причины выполнить новую заранее ограниченную серию, сохранив прежнюю.
4. Отдельно проверить негативные условия стенда подставными адаптерами из §5; не вмешиваться в реальный desktop пользователя ради создания отказов.
5. Выполнить ручную матрицу §5 основного ТЗ на одной идентифицированной публикации: Проводник/названный браузер, меню/подменю и способы закрытия, 20 переходов через настройки, трей/переключатели, 100 переключений, move/resize/закрытие цели, DPI/разрешение, штатный выход.
6. Реальный кандидат запускать после штатного завершения прежнего экземпляра: single-instance не должен подменить проверяемую версию старым процессом. Изменения системного DPI/разрешения выполнять в согласованном тестовом сеансе.

Если production-код не менялся, существующую публикацию разрешено использовать после проверки хешей. При изменении приложения подготовить отдельную папку кандидата с новым build-id и хешами; не переносить GUI-результаты между разными бинарниками.

Подготовить:

- Изменения тестового стенда и необходимые узкие адаптеры для проверок.
- `docs/TestCoverage_0.2.2.md` и папки результатов отдельных запусков.
- `docs/Validation_0.2.2.md` с командами, конфигурациями, идентификацией сборок, всеми результатами и открытыми блокерами.
- Ссылки из README и дополнение исторического `docs/Review_0.2.2.md`; прежние PASS и FAIL не удалять.
- Актуальные KnownLimitations. «Код написан», «сборка пройдена», «поведение проверено» и «принято» указывать раздельно.

**Критерий готовности:** оконный стенд детерминированно обрабатывает свои предусловия и отказы; контролируемые серии полностью проходят; карта не скрывает обязательных пробелов; ручная матрица 0.2.2 завершена с доказательствами. До выполнения этих условий статус приёмки остаётся открытым.

NU1900 фиксировать отдельно: недоступный аудит NuGet не является успешной проверкой уязвимостей. Ранее зарегистрированный дефект borderless fullscreen и длительные измерения общей версии 0.2 этим заданием не закрываются.

Производственный код менять только при обнаружении конкретного подтверждённого дефекта, необходимого для выполнения действующих требований; такой случай отдельно описать и повторить затронутые проверки. Не расширять функциональность и не переписывать работающую owner/Z-order-стратегию ради получения зелёного теста.
